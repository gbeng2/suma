# Staff knowledge base: business rules

This knowledge base lists the rules the suma software enforces, written for staff who are not engineers. There is one file per area. Each file is a set of tables, and each table row is one rule.

How to read a row:

- **Rule (plain English)**: what the software does or refuses to do.
- **Symptom staff would see**: what you or a member would notice when the rule applies, such as an error message or a missing item.
- **Fix in admin**: what to change in the admin app to resolve it. Some rows say an engineer is needed.
- **Severity**: `error` means something is blocked or broken, `warning` means it works but can surprise you, `info` is background knowledge.
- **file:line**: where the rule lives in the code. You can ignore it. Give it to an engineer if you need to ask about the rule.

A row marked **UNVERIFIED** could not be fully confirmed from the code. Treat it as a lead, and ask an engineer before relying on it.

Rules that involve two areas appear in both files, under "Cross-area rules". Each file ends with a "Skipped (plumbing)" list of code that was checked and holds no business rule.

## Top rules most likely to break things for members

1. **An offering with no programs attached is closed to every member**, even when its dates are right. A member can only see an offering, change the cart, start checkout, or place the order if they are eligible right now for at least one program attached to it. Otherwise they get a 403 "eligibility_violation" error ("Member cannot access due to constraints") and no order is created. Attach at least one program on the Offering page. (checkout, eligibility, offerings, orders, products, programs: `lib/suma/program/has.rb:23-39`; `lib/suma/eligibility.rb:13`; `lib/suma/api/commerce.rb:29,35-40,156-159`; `lib/suma/api.rb:49-52`)
2. **A program or payment trigger with no eligibility requirement is available to nobody in the live system.** A brand-new program, and every offering, vendor account, and mobility pricing attached only to it, shows for no members until a requirement is attached. Deleting or detaching the last requirement hides it from all members. (eligibility, programs: `lib/suma/eligibility.rb:13`; `lib/suma/eligibility/resource.rb:61-73`; `lib/suma/eligibility/evaluation.rb:75`)
3. **A requirement with an empty formula never passes, and every new requirement starts empty.** A formula saved while the editor shows an error is not saved, so the old (possibly empty) formula stays in place and nobody qualifies through it. (eligibility: `lib/suma/eligibility/evaluation.rb:38-39`; `lib/suma/eligibility/requirement.rb:67`; `lib/suma/admin_api/eligibility_requirements.rb:86-92`)
4. **Attributes from an organization count only when the member's membership in that organization is verified.** Unverified or removed memberships give no access to that organization's programs. A member who picked their organization but was not verified cannot see its programs, and a removed member loses them right away. (eligibility, organizations: `db/migrations/107_eligibility_attributes.rb:91-100`; `lib/suma/organization/membership.rb:32,54-60`)
5. **A member only gets a program while the current time is inside its period.** The moment the period ends, the program and everything attached only to it disappears from the app. (programs: `lib/suma/eligibility/resource.rb:36-48,77-78`)
6. **Members can only see and use an offering while the current time is inside its open period.** Outside it, the offering is missing from the list, and direct links, cart changes, and starting checkout return "Forbidden" (403). (offerings: `lib/suma/api/commerce.rb:29,36-37,82,98`; `lib/suma/commerce/offering.rb:149,166-168`)
7. **Text messages, including sign-in codes, are only sent to phone numbers on the engineers' SMS allow list, which is empty by default.** Other texts are aborted, so the member cannot sign in. No admin fix; an engineer is needed. (members: `lib/suma/message/transport/sms.rb:10-14,54-64`; `lib/suma/message/delivery.rb:57-66`)
8. **A member who is not verified is in read-only mode.** They can sign in and browse but cannot place an order or use services. At checkout they see a red "not verified" message and no button to place the order. Turn on "onboarding verified" on the member's admin page. (checkout, members: `lib/suma/member.rb:254-255,260-262`; `lib/suma/commerce/checkout.rb:117,176-181`; `webapp/src/pages/FoodCheckout.jsx:370-372,420-425`)
9. **A registration link auto-verifies a member only within 60 minutes of opening it (default), only inside its schedule, and only once per code.** A link with only half a schedule filled in never auto-verifies anyone, so those members stay read-only. The browser also remembers the code for only 1 hour, so a person who scans the link and finishes sign-up later is not auto-verified and does not get the organization's programs. Existing members who open the link outside its schedule see a link-invalid message. (members, organizations: `lib/suma/organization/registration_link.rb:60-62,79-88,121-127,139,146-161,167-168,186-191`; `lib/suma/api/me.rb:55-58`; `lib/suma/apps.rb:107-110`; `webapp/src/pages/PartnerSignup.jsx:37-48,74-76`)
10. **Closing an account frees the phone number.** If the person signs in again with the same phone, they get a brand-new, empty, unverified account. Old orders and balance stay on the closed account. The admin app shows no way to reopen a closed account. (members: `lib/suma/member.rb:428-436`; `lib/suma/api/auth.rb:64-71`; `lib/suma/admin_api/members.rb:237-250`)
11. **A product or service with no category cannot be paid for by any ledger, and it breaks the whole offering page.** Price calculation fails, and every member gets an "internal error" when viewing prices or checking out. The product form lets staff save a product without a category. Subsidy money also is not applied when the ledger and the item categories are not in the same branch. (payments, products: `lib/suma/payment/ledger.rb:209-235`; `lib/suma/admin_api/commerce_products.rb:54`)
12. **Checkout cannot start if any cart item has no open listing or its quantity is above the current maximum.** The maximum comes from stock, the per-member limit, the offering limits, or the default of 12. Limits are not checked when the cart is changed, only at checkout. A closed offering product gives the member "product unavailable" (409) until staff re-open the listing or the member removes the item. (checkout, offerings: `lib/suma/commerce/cart.rb:81-101,114-145,258-263`; `lib/suma/commerce/cart_item.rb:38-42`; `lib/suma/api/commerce.rb:103-108`)
13. **Stock and order limits are checked again when the order is placed, and eligibility is too.** If any item is over what is still allowed, no order is created and the member gets a 403 "max quantity exceeded" error. If the program closed or the member lost eligibility after starting checkout, the order is not placed. (checkout, orders, programs: `lib/suma/commerce/checkout.rb:246-256`; `lib/suma/api/commerce.rb:156-159,181-182`; `lib/suma/api.rb:49-52`)
14. **Checkout is refused when the amount the member was shown no longer matches what suma calculates at purchase time.** This happens when a balance or subsidy changed in between. The member sees "Checkout prohibited: charge_amount_mismatch" and must refresh. (payments: `lib/suma/commerce/checkout.rb:219-223`; `lib/suma/api/commerce.rb:173-174`)
15. **Order payment must be collected on the spot.** A declined card blocks the order. Paying by bank account outside banking hours (weekdays 9 am to 3 pm Eastern) fails with a generic server error. (payments: `lib/suma/commerce/checkout.rb:233-242`; `lib/suma/api/commerce.rb:175-180`; `lib/suma/payment/funding_transaction/increase_ach_strategy.rb:31-33`)
16. **When a member's "add funds" request fails for a payment reason, the member only sees a generic internal error (500).** This covers a declined card, an unverified bank account, and a member not set up with the card processor. No card message is shown, and nothing is saved. (payments: `lib/suma/api/payments.rb:18-28`; `lib/suma/service.rb:249-272`)
17. **A payment trigger (automatic subsidy or match) applies only while it is active and the member passes one of its requirements.** Otherwise the member pays full price or gets no match. (eligibility, payments: `lib/suma/payment/trigger.rb:19-22,36-39`; `lib/suma/payment/charge_contribution.rb:245`)
18. **Changing a price or closing an offering product while a member is checking out breaks that checkout.** The member gets "max quantity exceeded" (403) at the final step even though stock is available, and must start checkout again. Every save of the Update Offering Product form closes the listing and creates a new one, even with no price change, and resets the per-member purchase count. (offerings, products: `lib/suma/commerce/checkout.rb:118,246-256`; `lib/suma/commerce/cart.rb:115`; `lib/suma/commerce/offering_product.rb:90`; `lib/suma/api/commerce.rb:181-182`; `lib/suma/admin_api/commerce_offering_products.rb:39-49`)
19. **When a product has more than one listing in an offering (after a re-price or re-list), a cart item does not reliably use the open one.** A member with the product already in the cart can still get "product unavailable" or see the old price. No admin fix; an engineer is needed. (checkout: `lib/suma/commerce/cart_item.rb:14-36,38-42`; `lib/suma/commerce/cart.rb:65,260-264`)
20. **A negative customer price can be saved on an offering product.** Nothing stops staff from saving it. Members then get an "internal error" when opening the offering or checking out. (products: `lib/suma/admin_api/commerce_offering_products.rb:27-28`; `lib/suma/payment/account.rb:110`)
21. **A missing out-of-stock message gives members an "internal error" (500) instead of the offering page.** This happens when a product has no text for its out-of-stock reason and the "cart_quantity_reason.out_of_stock" static string is also missing. (checkout: `lib/suma/commerce/cart.rb:153-155`; `lib/suma/i18n/static_string.rb:61-64`; `lib/suma/postgres/model_utilities.rb:171-180`; `lib/suma/service.rb:249-272`)
22. **Once the offering's "max ordered items cumulative" total is reached, every product in the offering shows as out of stock for everyone.** Canceled orders do not count toward the total. (offerings: `lib/suma/commerce/cart.rb:131-133`; `lib/suma/commerce/offering.rb:113,140-146`)
23. **With Limited Quantity on, a product is out of stock when Quantity On Hand minus Quantity Pending Fulfillment is zero or less.** Members see "Out of stock" and cannot order it. Staff can type any number into these fields, including a wrong one. (products: `lib/suma/commerce/cart.rb:122-123`; `lib/suma/admin_api/commerce_products.rb:55-60`)
24. **Placing an order holds stock, and cancel and fulfillment steps done in the wrong order leave the held number wrong.** "Quantity pending fulfillment" goes up when an order is placed. Pressing "unfulfill" after canceling a fulfilled order leaves stock held forever, so a limited-quantity product looks out of stock when it is not. (orders: `lib/suma/commerce/order.rb:109-112,143,182-188`; `lib/suma/commerce/checkout.rb:258`)
25. **If the offering has no "begin fulfillment at" time, orders never start fulfillment on their own.** They sit at "unfulfilled" and members never get a "claim" option until staff press "begin fulfillment" on each order. (orders: `lib/suma/commerce/order.rb:216`; `lib/suma/commerce/offering.rb:162-164,177`; `lib/suma/async/offering_schedule_fulfillment.rb:15`)
26. **A member can claim an order only while it is "fulfilling" and only for pickup (or no fulfillment option).** Delivery orders can never be claimed by the member; staff must use "end fulfillment". Otherwise the member gets a 409 "Order cannot be claimed" error. (orders: `lib/suma/commerce/order.rb:104-106,220-226`; `lib/suma/api/commerce.rb:242-246`)
27. **Using a vendor service, such as starting a mobility trip, is refused in three cases.** The member is read-only, their cash balance is below the minimum for services (default $0, so any negative balance; code "usage_prohibited_cash_balance"), or the service costs money (an unlock fee or per-minute price above $0) and they have no working payment method on file (code "usage_prohibited_instrument_required"). A balance that has stayed negative for the whole grace period (default 18 hours) also blocks use. The map shows the service as unavailable, and the member also cannot link private accounts. For Lime and Lyft this means the member cannot ask for a Lime sign-in link, or link or re-link their Lyft account, while the balance rules block them or (for Lime) they have no payment account; they see "Account cannot use services" (402). (lime, lyft, members, mobility, payments, programs, vendors: `lib/suma/vendor/service.rb:47-50,54-61`; `lib/suma/mobility/trip.rb:61`; `lib/suma/payment.rb:45,70,119-159`; `lib/suma/member.rb:286-289`; `lib/suma/api/anon_proxy.rb:38-42`)
28. **A member only sees vehicles from services that have a program pricing the member is eligible for, and only between the service's period begin and period end dates.** Otherwise the map is empty or a vendor is missing. (mobility: `lib/suma/api/mobility.rb:13-17,42-43`; `lib/suma/program/pricing.rb:20-25`)
29. **Vehicles are loaded from a vendor's vehicle feed only for services that carry the "mobility" category.** Without it, no scooters or bikes from that vendor ever appear on the member map. (vendors: `lib/suma/mobility/gbfs/vendor_sync.rb:10`)
30. **A service whose vehicles show on the map must have a Mobility adapter setting other than "No Adapter/Non-Mobility".** Otherwise a member who taps a vehicle gets a server error. (vendors: `lib/suma/api/mobility.rb:281`)
31. **A private account setup with no programs attached is hidden from every member, even when it is Enabled.** No vendor card shows and no private accounts are created. Attach at least one program. The Lime card and the Lyft card are also hidden when the setup is not Enabled, when the member is not verified, or when the member does not qualify for any program attached to the setup. (lime, lyft, vendors: `lib/suma/program/has.rb:36-39`; `lib/suma/anon_proxy/vendor_account.rb:40-44`)
32. **When a member qualifies for more than one price on the same service, the map shows the price from the rate with the highest ordinal (ordering number), but the Lime trip import charges using the rate with the lowest ordinal.** The member can be charged a different price than the map showed. Editing a rate may also reset its ordinal to 0 unless it is re-entered (this part is UNVERIFIED; check the ordinal after every rate edit). (mobility, vendors: `lib/suma/api/mobility.rb:41-42`; `lib/suma/lime/sync_trips_from_report.rb:196`; `lib/suma/program/pricing.rb:24`; `lib/suma/admin_api/vendor_service_rates.rb:51`)
33. **Each Lime report email is read only once, and a report that stops with an error part-way is retried every 30 minutes while newer reports wait behind it.** One bad report (for example a trip whose lines add up to less than $0, or a member with no clear program pricing) stops all Lime trips from importing and being charged. An engineer is needed. The "no clear program pricing" case is a rider who was not eligible, where the Lime setup's programs had zero prices, or more than one different price, for the trip date. (lime, mobility: `lib/suma/webhookdb.rb:54-61`; `lib/suma/lime/sync_trips_from_report.rb:172-174,207-214`; `lib/suma/mobility/trip.rb:102-103`)
36. **A Lime sign-in link that arrives while the member no longer qualifies, or while the balance rules block them, is not passed on.** It is not put in the Magic Link field and is not sent to the member. Lime's email is only kept in the account's message history. (lime: `lib/suma/anon_proxy/message_handler/lime.rb:52-70`; `lib/suma/anon_proxy/message_handler.rb:44-49`)
37. **Free minutes on a rate ("unit offset") are not taken off imported Lime trips.** The member pays the per-minute price for every minute, so they are charged more than staff expect. (lime: `lib/suma/mobility/trip_importer.rb:92-97`; `lib/suma/lime/sync_trips_from_report.rb:269-271`)
38. **A wrong Lyft Pass Program ID on one program stops the whole Lyft trip import at the first error from Lyft.** Members who qualify for that program also get a server error when they press link. suma does not check the ID when staff save it. (lyft: `lib/suma/lyft/pass.rb:280-288`; `lib/suma/async/lyft_pass_trip_sync.rb:17-19`; `lib/suma/anon_proxy/auth_to_vendor/lyft_pass.rb:13-17`)
39. **A Lyft Pass program must have exactly one pricing.** Zero or more than one stops the whole Lyft import run, so no Lyft or Biketown trips appear for any program. (lyft: `lib/suma/lyft/pass.rb:299-302`; `lib/suma/enumerable.rb:21-24`)
40. **Two suma programs whose Lyft programs share one Lyft owner account get the same rides.** Each ride is saved under whichever program is handled first, so members can see the wrong service, rate, or extra charge or discount lines. (lyft: `lib/suma/lyft/pass.rb:245`; `lib/suma/lyft/pass.rb:308-317`; `lib/suma/lyft/pass.rb:359`)
34. **Approving a verification only works when the membership is already verified or the typed organization name exactly matches an existing organization.** A name that differs by one character (or "unaffiliated" / "not listed") leaves the member stuck unverified. Fix the organization name on the membership first. (organizations: `lib/suma/organization/membership/verification.rb:122-125,145`; `lib/suma/organization/membership.rb:68-71`)
35. **An existing, already-onboarded member who scans a registration link only becomes a verified member when they press accept.** Going to the dashboard instead leaves them with no membership in the organization. (organizations: `webapp/src/pages/PartnerSignup.jsx:50-51,80-115`; `lib/suma/api/me.rb:55-56`)
